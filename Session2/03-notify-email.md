# 手順 3（発展・任意）：会員登録のあとにメールを送る（DynamoDB ストリーム + SES）

会員が新しく登録されたら、その会員に「登録完了メール」を自動で送る仕組みを追加します。会員登録の Lambda（`users-function-<名前>`）は書き換えません。DynamoDB の「変更の記録」をきっかけに、別の Lambda がメールを送ります。

この手順は **任意** です。飛ばしても Session3 以降は進められます。

```text
Lambda（users-function-<名前>）    … 会員を登録する（これまでの手順で作成済み）
   │ 保存
   ▼
DynamoDB（users-table-<名前>）
   │ ストリーム（変更の記録）
   ▼
フィルター（INSERT＝新規登録だけ通す）
   │
   ▼
Lambda（users-notify-function-<名前>）  … この手順で作成
   │
   ▼
Amazon SES  ──▶  会員のメールアドレスに登録完了メール
```

**始める前に**: Session2 の [2-7](02-lambda.md#2-7-テストしてみるlambda-単体) まで終わっていること。Session3 の前でも後でも試せます（API がなくても、Lambda のテストだけで確認できます）。

## 用語

| 用語 | 意味 |
|---|---|
| DynamoDB ストリーム | テーブルの「追加・変更・削除」を、順番に記録しておく仕組みです。記録は 24 時間保存されます |
| イベントソースマッピング | ストリームを見張り、新しい記録が出たら Lambda を呼び出す設定です。Lambda の画面では「トリガー」として表示されます |
| Amazon SES | AWS のメール送信サービスです（Simple Email Service の略） |
| サンドボックス | SES を使い始めたときの「お試し状態」です。送信元と宛先の両方が、確認済みのアドレスである必要があります |
| 確認済み ID | 「このメールアドレスは自分のものです」と SES で確認が済んだアドレス（またはドメイン）です |
| 少なくとも 1 回（at-least-once） | ストリームの記録は「最低 1 回は Lambda に届く」という約束です。再試行などで、**まれに同じ記録が 2 回届く** ことがあります |

## 3-1. SES で送信元のメールアドレスを確認する

メールを送るには、送信元のアドレスが自分のものであることを SES に確認してもらいます。

1. 検索欄に **SES** と入力し、**Amazon Simple Email Service** を開く
2. リージョンが **アジアパシフィック（東京）ap-northeast-1** であることを確認する
3. 左のメニューの **ID**（Identities）→ **ID の作成**（Create identity）
4. ID の種類で **E メールアドレス**（Email address）を選び、自分のメールアドレスを入力する
5. **ID の作成** をクリック
6. 入力したアドレスに、AWS から確認メールが届きます。メール内のリンクをクリックする
7. SES の画面を再読み込みし、そのアドレスの **ステータス** が **確認済み**（Verified）になっていることを確認する

> **ポイント**: 最初の SES は **サンドボックス** です。宛先も確認済みのアドレスでなければ送れません。この教材では、**自分のアドレス 1 つを送信元と宛先の両方に使います**（1 回確認すれば、どちらにも使えます）。
> 確認していないアドレスに送るには、SES の「本番アクセス」の申請が必要です。この教材では扱いません。

> 画面の表記が少し異なる場合は、カッコ内の英語表記を目安に進めてください。

### 確認ポイント

- [ ] リージョンが ap-northeast-1
- [ ] 自分のアドレスのステータスが **確認済み**

## 3-2. DynamoDB のストリームを有効にする

1. DynamoDB の画面 → **テーブル** → `users-table-<名前>` を開く
2. **エクスポートおよびストリーム**（Exports and streams）タブを開く
3. **DynamoDB ストリームの詳細**（DynamoDB stream details）の **オンにする**（Turn on）をクリック
4. 表示タイプ（View type）で **新しいイメージ**（New image）を選ぶ
5. **ストリームをオンにする**（Turn on stream）をクリック

> **新しいイメージとは？**
> 保存された「後」の項目の中身を、記録に入れる設定です。通知用の Lambda は、ここから `name`（氏名）と `email` を読み取ります。

### 確認ポイント

- [ ] DynamoDB ストリームが **オン**、表示タイプが **新しいイメージ**

## 3-3. 通知用の Lambda を作る

[2-2](02-lambda.md#2-2-関数を作成する) と同じ方法で、もう 1 つ関数を作ります。

| 項目 | 入力する値 |
|---|---|
| 関数名 | `users-notify-function-<名前>` |
| ランタイム | **Python 3.12** |
| アーキテクチャ | **x86_64** |
| 実行ロール | **基本的な Lambda のアクセス権限で新しいロールを作成** |

### コードを貼り付ける

1. **コード** タブで `lambda_function.py` を開く
2. **いま作った新しい関数**の `lambda_function.py`（最初から入っているサンプルコード）を、すべて消す。そこに `Session2/notify_function.py` のコードをすべて貼り付ける（会員登録用の `users-function-<名前>` は変更しません）
3. **Deploy（デプロイ）** をクリック

> **注意**: 貼り付け先のファイル名は `lambda_function.py` のままにします。ハンドラーは初期値の `lambda_function.lambda_handler` のままで動きます（[2-4](02-lambda.md#2-4-ハンドラーを確認する) と同じ考え方です）。

### 環境変数を設定する

**設定** タブ → **環境変数** → **編集** で、次を追加して **保存** します。

| キー | 値 | 説明 |
|---|---|---|
| `SENDER` | 3-1 で確認したアドレス | 送信元のメールアドレス（必須） |
| `MAIL_MODE` | `ses` | 省略すると `ses` になります。メールを使えない環境では `log`（3-7） |
| `SES_REGION` | （通常は設定しない） | 任意。SES を使うリージョンです。省略すると `ap-northeast-1` になります。別のリージョンで SES を確認した場合だけ設定します |

### 確認ポイント

- [ ] 関数名が `users-notify-function-<名前>`、ランタイムが Python 3.12
- [ ] ハンドラーが `lambda_function.lambda_handler`
- [ ] 環境変数 `SENDER` に確認済みのアドレスが入っている

## 3-4. 実行ロールに権限を付ける

通知用の Lambda には、「ストリームを読む権限」と「SES でメールを送る権限」が必要です。**3-5 のトリガー追加より前に** 設定してください（トリガーを作るとき、ストリームを読む権限があるかが確認されるためです）。

### ストリームを読む権限

1. `users-notify-function-<名前>` の **設定** タブ → **アクセス権限** → **ロール名** のリンクをクリック
2. **許可を追加** → **ポリシーをアタッチ**
3. `AWSLambdaDynamoDBExecutionRole` を検索してチェックを付け、**許可を追加**

> `AWSLambdaDynamoDBExecutionRole` は、DynamoDB ストリームの読み取りと、CloudWatch Logs への書き込みができる AWS 管理ポリシーです。

### SES でメールを送る権限

1. 同じロールの画面で **許可を追加** → **ポリシーをアタッチ**
2. `AmazonSESFullAccess` を検索してチェックを付け、**許可を追加**

> **ポイント**: この研修は開発用なので、設定の手間を減らすために、SES の AWS 管理ポリシー `AmazonSESFullAccess`（SES のすべての操作を許可）を付けます。
> 本番の環境では、必要な権限だけに絞ります。たとえば `ses:SendEmail` だけを許可し、`ses:FromAddress`（送信元アドレス）の条件で「このアドレスからしか送れない」ようにします。サンドボックスでは宛先の ID も権限の確認の対象になるため、`Resource` は `*` にします。

### 確認ポイント

- [ ] ロールに `AWSLambdaDynamoDBExecutionRole` が付いている
- [ ] ロールに `AmazonSESFullAccess` が付いている

## 3-5. トリガー（イベントソースマッピング）を追加する

1. `users-notify-function-<名前>` の **設定** タブ → **トリガー** → **トリガーを追加**
2. ソースに **DynamoDB** を選び、次のとおり設定する

| 項目 | 値 | 説明 |
|---|---|---|
| DynamoDB テーブル | `users-table-<名前>` | 見張るテーブル |
| トリガーを有効化（Activate trigger） | チェックを付ける | すぐに動き始めます |
| バッチサイズ（Batch size） | `1` | 1 回の呼び出しで渡す記録の数 |
| 開始位置（Starting position） | **最新**（Latest） | これから起きる変更だけを扱います（過去の記録は扱わない） |
| バッチウィンドウ（Batch window） | 空欄（使わない） | 記録をためずに、すぐ呼び出します |

3. **追加の設定**（Additional settings）を開き、次を設定する

| 項目 | 値 |
|---|---|
| 再試行（Retry attempts） | `2` |
| フィルター条件（Filter criteria） | `{"eventName": ["INSERT"]}` |

4. **追加** をクリック
5. トリガーの状態が、しばらく「作成中」「有効化中」などと表示されます。**画面を再読み込みして、状態が『有効』になるまで待ってから** 3-6 に進んでください

> **注意**: 開始位置が **最新**（Latest）なので、トリガーが有効になる前に登録した会員は、メールの対象になりません。

> **ポイント**: フィルター条件で **INSERT（新規登録）だけ** を Lambda に渡します。更新（MODIFY）や削除（REMOVE）のときは、Lambda は呼ばれません。コードの中でも念のため INSERT 以外は無視しています。

> 画面の表記が少し異なる場合は、カッコ内の英語表記を目安に進めてください。権限のエラーが出たら、3-4 が済んでいるか確認してください。

### 確認ポイント

- [ ] トリガーの一覧に DynamoDB（`users-table-<名前>`）があり、再読み込みしても状態が **有効**（Enabled）（有効になる前に会員を登録しない）
- [ ] フィルター条件が `{"eventName": ["INSERT"]}`

## 3-6. 動作を確かめる

### (1) 会員を登録して、メールが届くか確かめる

1. 会員登録の Lambda `users-function-<名前>` を開き、[2-7](02-lambda.md#2-7-テストしてみるlambda-単体) と同じ方法でテストする
2. テストイベント（`test-events/create-user.json` の中身）の `body` を、次のように書き換えてから **テスト** をクリック
   - `body` は、JSON を文字列にした「エスケープ済み」の値です（`"{\"id\": ...}"` のように `\"` が並びます）。書き換えるのは `\"...\"` の **中の値だけ**（メールアドレスと id）で、バックスラッシュ `\` は消さずに残してください
   - `email` を、3-1 で確認した自分のアドレスにする
   - `id` を新しい値にする（例: `u-0002`）。2-7 と同じ `id` だと `409`（同じ ID がすでにある）になり、保存されません
3. `statusCode: 201` になったら、数秒〜1 分ほど待つ
4. 件名 `【View AWS勉強会サイト】会員登録が完了しました` のメールが届けば成功です。届かないときは **迷惑メールフォルダ** も確認してください

> Session3 の後なら、サイトの会員登録画面から登録しても同じようにメールが届きます。

### (2) 通知用 Lambda のログを確かめる

1. `users-notify-function-<名前>` → **モニタリング** タブ → **CloudWatch Logs を表示**
2. 新しいログストリームを開き、`メールを送信しました id=u-0002 MessageId=...` のような行があることを確認する

> 個人情報を残さないために、メールアドレスはログに出さない作りになっています。SES がエラーを返したときも、ログと実行結果に出るのはエラーコードだけです（詳しい理由の文面は、宛先のアドレスを含むことがあるため、あえて出していません）。

### (3) 更新ではメールが送られないこと

同じ会員を更新（PUT など、上書き保存）しても、記録は INSERT ではなく MODIFY なので、メールは送られない設計です。

### (4) 通知用 Lambda だけをテストする

DynamoDB を使わずに、通知用の Lambda だけを試すこともできます。

1. `users-notify-function-<名前>` の **テスト** タブ → **新しいイベント**、イベント名 `stream-insert`
2. `Session2/test-events/stream-insert.json` の中身を貼り付け、`"email": { "S": "taro@example.com" }` を **自分の確認済みアドレス** に書き換える
3. **保存** → **テスト**。実行結果が `{"sent": 1, "skipped": 0}` になり、メールが届けば成功です

### 確認ポイント

- [ ] 新しい会員の登録後、登録完了メールが届いた
- [ ] 通知用 Lambda のログに「メールを送信しました」が出ている

## 3-7. メールが使えない環境のとき

会社のメールで外部からのメールを受け取れないなど、SES を使えないときは、`MAIL_MODE` を `log` にします。

1. 通知用 Lambda の環境変数 `MAIL_MODE` を `log` にして保存する
2. 3-6 と同じように会員を登録する
3. CloudWatch Logs に `[MAIL_MODE=log]` から始まる行と、メールの件名・本文が出れば成功です

- `log` のときは SES を呼ばないので、3-1（SES の確認）と SES の権限（`AmazonSESFullAccess`）は不要です。`SENDER` も省略できます
- **注意**: ログに氏名などの個人情報が出ます。練習用のデータだけで使ってください

## 重複・失敗の扱い

- ストリームは **少なくとも 1 回** 届ける仕組みです。再試行などで、まれに同じメールが 2 通届くことがあります。教材ではそのまま受け入れます（本番では「送信済み」の記録を残して重複を防ぐなどの工夫をします）
- SES の送信が失敗すると、Lambda は `SES の送信に失敗しました code=...` というエラーになり、同じ記録で **最大 2 回** 再試行します
- 再試行しても失敗したときは、その記録は捨てられて次の記録に進みます（失敗した記録を別の場所に残す方法は、この教材では扱いません）
- メールアドレスがない記録は、再試行しても直らないため、ログに警告を出して飛ばします

## よくあるエラー

| 症状・エラー | 原因と対処 |
|---|---|
| `SES の送信に失敗しました code=MessageRejected` | 送信元か宛先のアドレスが確認されていません（サンドボックス）。SES の本来のメッセージは宛先アドレスを含むため、ログには出していません。ログではなく、SES の **ID** 画面で送信元と宛先のステータスが **未確認** になっていないか、登録した `email` が正しいかを確認します |
| `SES の送信に失敗しました code=AccessDenied` | 3-4 で、ロールに `AmazonSESFullAccess` が付いているか確認します（詳しい文面は、アドレスを含むためログに出していません） |
| ログに「メールアドレスがない」という警告が出て、すべての記録が飛ばされる | DynamoDB ストリームの表示タイプが **新しいイメージ** になっていません（「キーのみ」などだと `email` が記録に入りません）。3-2 で表示タイプを **新しいイメージ** に設定し直し、会員を登録し直します |
| トリガーの追加で権限のエラー | 3-4 の `AWSLambdaDynamoDBExecutionRole` を先に付けてから、トリガーを追加し直します |
| `SENDER（SES で検証済みの送信元アドレス）が設定されていません` | 3-3 の環境変数 `SENDER` を設定します |
| `MAIL_MODE は ses か log を指定してください` | `MAIL_MODE` の値の綴りを確認します |
| メールが届かない | 迷惑メールフォルダを確認します。同じ `id` で登録すると `409` になり、保存されないためメールも出ません。トリガーが **有効** か、フィルター条件が正しいかも確認します |
| 同じメールが 2 通届いた | 「少なくとも 1 回」の仕組みによるもので、まれに起こります（上の「重複・失敗の扱い」） |

## 片付け（使い終わったら）

次の順番で削除します。

1. `users-notify-function-<名前>` → **設定** → **トリガー** で、DynamoDB のトリガーを削除する
2. Lambda `users-notify-function-<名前>` を削除する
3. IAM → 自動で作られた実行ロール（`users-notify-function-<名前>-role-xxxx`）を削除する
4. DynamoDB → `users-table-<名前>` → **エクスポートおよびストリーム** で、ストリームをオフにする
5. SES → **ID** で、確認済みのアドレスを削除する（任意）

> Session3 などの片付けで `users-table-<名前>` を削除するときは、**先にこのトリガーを削除** してください。テーブルを Session4 以降でも使う場合は、ストリームとテーブルはそのままでかまいません。

## 料金と注意

- 練習程度の少ない量なら、Lambda・SES・DynamoDB ストリームの料金はごくわずかです（無料枠の範囲に収まることが多いです）。使い終わったら片付けてください
- この仕組みは、氏名とメールアドレスという **個人情報** を扱います
- 宛先には **練習用の自分のアドレス** を使い、実在する他人のアドレスには送らないでください
